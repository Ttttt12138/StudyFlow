# Internationalization

The API supports Simplified Chinese and English. The language is negotiated from the `Accept-Language` request header (Django `LocaleMiddleware`); unsupported languages fall back to English.

## Error responses

Every error returned through DRF gains two fields in addition to the existing ones. The existing `detail` is unchanged, so clients and tests can keep matching on it:

```json
{"detail": "QUOTE_EXPIRED", "code": "QUOTE_EXPIRED", "message": "报价已过期，请重新获取报价。"}
```

(The `message` above is the Chinese localization, meaning "The quote has expired. Please get a new quote.")

| Field | Description |
|---|---|
| `detail` | Original value: a stable error code (upper case with underscores), or an English sentence from older endpoints |
| `code` | Machine-readable error code. Same as `detail` when `detail` is itself a code; otherwise the DRF error category (such as `invalid`, `not_found`, `stale_version`) |
| `message` | Explanation in the negotiated language, intended for end users |

The `Content-Language` response header states the language actually used. Field-level validation errors (`{"field": ["..."]}`) keep DRF's original format. Other fields, such as the `policy` object of a permission denial, are kept as they are.

## Translation catalogs

- `backend/locale/zh_Hans/LC_MESSAGES/django.po`: Chinese translations of all error codes and English sentences.
- `backend/locale/en/LC_MESSAGES/django.po`: English explanatory sentences for error codes.

The catalogs are extracted automatically from source code by `backend/scripts/i18n_messages.py`:
- Extraction targets the string arguments of exceptions such as `require(condition, "…")` and `PolicyDenied("CODE")`, plus exception classes' `default_detail`.
- Extraction keeps existing translations; compilation uses Babel, so GNU gettext does not need to be installed.

```bash
python scripts/i18n_messages.py extract
```

```bash
python scripts/i18n_messages.py compile
```

```bash
python scripts/i18n_messages.py check
```

`check` runs in the local gate and in CI: it fails when the code contains new error text that the catalogs lack, when entries are untranslated, or when the `.mo` files were not recompiled. An error code missing from the catalogs never returns an empty message; the code is turned into readable text as a fallback.

## Other localization

- Agent sessions: when the request body has no `locale`, the answer language follows the negotiated language (`zh*` → Chinese, anything else → English).
- The planner prompts and the rule-based planner accept Chinese, English and mixed input (see [Agent](agent.md)).
- The OCR notice already provides bilingual Chinese and English text (see [Gemini OCR](gemini-ocr.md)).
- Amounts and dates stay decimal strings and ISO dates in the API; clients format them by language.

## Frontend

- An English / 中文 (Chinese) switch is always available: in the simulated-funds strip at the top of the app (`frontend/src/services/SimulatedStrip.tsx`) and in the intro page navigation (`frontend/src/intro/IntroNav.tsx`). The default follows the browser language (`zh*` → Chinese, anything else → English); the user's choice is saved in this browser's `localStorage` (`studyflow.lang`), and if reading or writing fails the default is used without affecting the app.
- Implemented in `frontend/src/i18n/`: `useI18n()` returns `{lang, setLang, t}`; each feature has its own dictionary file (for example `common`, `plan`, `price`, `loans`, `loanAdvice`, `life`, `wallet`, `payments`, `agent`, `trust`, `operations`), merged in `messages.ts`. The Chinese dictionary is typed against the English one, so any missing translation fails `tsc`.
- The API client sends `Accept-Language` (`en` or `zh-Hans`) on every request, so the backend's `message` matches the interface language; agent sessions explicitly pass the current interface language as `locale`.
- Dates are formatted by interface language (`zh-CN` / `en`); amounts keep the "currency + number" format, identical in both languages.
- Browser tests pin `en-US`, and Vitest pins English through `src/test-setup.ts`; several mocked Playwright specs (for example `frontend/tests/e2e/mocked/plan.spec.mjs`) also switch to Chinese with the 中文 button.

## Scope limits

Explanatory text assembled in code by the readiness and consumption modules (briefings, notifications, calendar labels; retired from the product on 2026-10-15; backend only) is still English and was not translated. Backend data shown in the frontend (such as sample school names, cost item names, and step rationales written by the mock planner) is displayed as returned, without translation. Translations were made by AI and have not been reviewed by a native speaker.

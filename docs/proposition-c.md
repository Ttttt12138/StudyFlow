## 逐项说明

### 1. 多币种核心
- 钱包按币种记账：本币 THB 仍记在 `DemoWallet.balance`，外币记在 `WalletBalance`。两类余额都有数据库约束保证不为负。
- 所有余额变化只能经过 `wallets.post` 一个入口。
- 账本分录带币种；按币种汇总的分录合计等于该币种余额，这条不变量有测试覆盖。
- 汇路（`Corridor`）共 12 条，覆盖 CNY/USD/EUR→THB 与 THB→CNY，每个方向各有 express、standard、economy 三档。
- 自有余额之间换汇只接受服务端定价的报价，报价只能结算一次。
- 本币暂时固定为 THB，原因是借款核心 B 只支持 THB；其他币种可配置。

### 2. 汇款订单状态机
- 状态共 9 个：CREATED → SUBMITTED → IN_TRANSIT → DELIVERED → RECONCILED，另有 CANCELLED、EXPIRED、UNKNOWN、REFUNDED。
- 每次状态转换都检查版本号，并写入不可修改的状态历史。
- 资金：提交时扣款；失败时全额退回；汇给自己的订单送达时入账。账本按"扣款、退回、入账"三种分录记录，每张订单每种分录最多一条。
- 费用明细包括发送费、汇率点差成本和总成本；汇路的金额上下限会在提交时再次校验。
- 联动：状态为已退回或状态不明的订单会进入复核队列；按期送达的订单计入信用记录。
- 学费：没有独立的学费模块。学费通过两条现有资金流程支付，两者都要求收款方已核验：
  - 汇款订单 `purpose=tuition`、`recipient=BENEFICIARY`，创建和提交时都校验受益人 `verified`（`finance/remittance_orders.py`）；
  - readiness 付款 `POST payments/`，要求已确认发票和受控核验收款人，回执按发票对账（[消费与执行](consumption.md#模拟汇款与学费执行)、`finance/execution_services.py`）。

### 3. 汇率接入
- 通过 C 模块已有的 Frankfurter 适配器获取参考汇率（Frankfurter v2 汇总多家央行，含 ECB、泰国央行、中国外汇交易中心），并保存为快照，15 分钟内复用。2026-10-07 已用真实网络验证。
- 获取失败时退回最近一次快照；汇率超过 7 天视为过期，不能用来生成报价。
- CI 默认使用固定汇率（`STUDYFLOW_FX_LIVE=false`），不发起外部请求。
- 文档和接口响应中都如实标注这是"参考价"，不是可成交的实时价。

### 4. 权限分级
- **分级**：T0 只读；T1 写入但资金不离开钱包；T2 资金流出，需要二次验证（重新输入密码，签发 5 分钟一次性令牌，与动作、目标、金额、币种绑定）；T3 超出限额，还需要运营人员审批。
- **限额**：按币种设置单笔、单日、单月三档，按曼谷时区计算；实际限额再乘以信用档案对应的系数。
- **分权**：审批人不能是申请人，不能是该收款人的核验人，也不能审批自己名下的申请。
- **限流**：按作用域区分（登录、二次验证、资金操作、资助确认），计数存在共享的数据库缓存里。
- **纳入分级的动作**：付款提交、换汇、还款、汇款提交、Agent 待确认动作的确认。

### 5. 已知风险清单
- 汇总在 [known-risks.md](known-risks.md)，按资金、权限、部署、AI、OCR、工程六类列出。每条写明等级、现有缓解措施、状态和证据位置。
- 每个阶段结束时都会更新；本轮审查中发现的问题（例如自定汇率造钱）也已记录在内，并注明修复情况。

### 6. 生产加固
- 设置 `DJANGO_SECURE=true` 后启用以下配置：HTTPS 重定向、HSTS、安全 Cookie、CSRF 可信来源、nosniff、Referrer-Policy、`X-Frame-Options: DENY`、会话过期。
- 代理层数通过 `DJANGO_NUM_PROXIES` 配置，防止客户端伪造 `X-Forwarded-For` 绕过限流。
- CI 会以加固模式运行 `check --deploy --fail-level WARNING`。

### 8. 工具调用 Agent
- **规划器**：C 模块每一步只返回一个工具调用或最终回答，使用结构化输出，不依赖网关是否支持原生 tools。CI 使用确定性的规则规划器。
- **工具**：共 11 个（T0 七个、T1 两个、T2 两个）。T2 工具只生成待确认动作，学生本人二次验证后才执行；确认时按它代理的底层动作做权限清算。
- **执行循环的强制约束**：
  - 最多 10 次工具调用、4 次写操作；
  - 拒绝未知工具和格式不对的参数；
  - 同一工具连续失败两次，或排序后没有能按期到账的渠道时，强制结束；
  - 工具结果截断到 4000 字符以内。
- **评估**：任务集共 20 个案例，覆盖中文、英文和中英混合，其中 3 个是提示注入样本。越权动作必须为 0，这一条是 CI 门禁。

### 9. 多语言
- 语言按 `Accept-Language` 在中文和英文之间协商。
- 错误响应保持原有的 `detail` 不变，另加错误码 `code` 和本地化的 `message`。
- 翻译目录由脚本从代码中自动抽取，用 Babel 编译，CI 检查目录是否完整。
- Agent 会话按协商语言回答。

### 10. 信用建立
- 统计平台内的准时记录：分期还款、账单付款、带截止日的汇款。时间窗口为 365 天，未处理的逾期记录不会随时间移出。
- 分为 BUILDING、FAIR、GOOD、AT_RISK 四档，分别对应限额系数 1.0、1.2、1.5、0.5。
- 可以生成不可修改的快照，并签发签名证明；任何人无需登录即可验证证明是否有效。
- 明确标注为模拟，不是征信评分。

工作方式：
- 每个功能先写规格文档，再由独立的代理只根据规格写测试，实现者另一人。
- 这些独立测试共发现并修复了多处实现问题，包括：
  - 自定汇率可以凭空造钱（高危）；
  - 过期订单未在所有命令下转为 EXPIRED；
  - 信用证明验证接口可能返回 500；
  - Agent 执行循环信任规划器的输出；
  - 整体安全审查发现的 3 个中危问题：信用等级可被低价刷高、拨快演示时钟可让逾期记录失效、汇款审批缺少"核验人不能审批"的分权规则。
- 合并前另派上下文干净的代理审查改动。

## 主要剩余风险

详见 [已知风险](known-risks.md)，最关键的几项：
- 所有资金和通道都是模拟的；汇款送达由运营人员回调触发。
- 二次验证只是重新输入密码，不是独立的第二因素；运营人员只有一种角色。
- Agent 真实模型在冻结集 agent-v2 上首次运行完成率 75%（18/24），越权动作 0；1 个注入案例中 Agent 向名称含注入文本的收款人提议了付款（未动资金，仍需学生二次验证）；模型偶尔把内部推理当作回答输出；两个评估集都由同一 AI 编写、未经人工审核。
- 参考汇率不是可成交价；加固配置未在真实 HTTPS 部署上验证。
- 翻译未经母语人工审校；briefing、通知等拼接文本仍为英文。

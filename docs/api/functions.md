# StudyFlow Backend Function Reference

This document describes the implemented application functions. Test functions,
migrations generated by Django, and standard framework internals are omitted unless
they enforce a system rule.

## Deterministic calculation functions

### forecast(snapshot, end_date, include_estimates=False)

Location: finance/calculations.py

Calculates a THB cash-flow timeline from one immutable financial-state snapshot.

Inputs:

- snapshot: opening balance, reserve, as-of date, and dated events.
- end_date: final included date, no more than 730 days after as_of.
- include_estimates: whether estimated events participate in the calculation.

Outputs:

- Ending and minimum balance.
- Maximum cash shortfall and maximum reserve gap.
- First reserve-gap date.
- Ordered event timeline with balance_after and reserve_gap.
- Missing and excluded estimated event IDs.
- Calculation status and explicit assumptions.

Ordering rules:

- Settled events use their database ledger sequence.
- Future expenses occur before future income on the same date.
- Events outside the requested horizon do not make that horizon incomplete.
- Missing dates remain incomplete because their timing is unknown.

Formula:

    balance(t) = opening balance + included income through t - included expenses through t
    cash shortfall(t) = max(0, -balance(t))
    reserve gap(t) = max(0, reserve - balance(t))

This function has no database side effects.

### loan_schedule(data)

Location: finance/loan_engine.py. Calls `finance.lending_core.calculations.calculate` with B's `QuoteInput` (THB, principal, annual_rate as a fraction, fees, months 1–60, first_due_date). The result includes the original B repayments and an identical schedule projection for Django budgets. No grace/foreign-currency loan arithmetic remains in the runtime. Current affordability is calculated by finance/affordability.py from versioned monthly profiles and other unpaid commitments.

## Budget and funding service functions

Location: finance/budget_services.py

### create_fx(actor, data, obj=None)

Creates an owned, explicitly mock FX quote. It validates direction, currency
precision, expiry within 30 days, fees, and settlement delay. THB-to-THB quotes are
rejected. A corresponding audit event is created.

### convert(owner, amount, currency, quote_id=None, expense=False)

Converts a supported amount into THB with exact Decimal arithmetic.

Funding formula:

    net THB = (source amount - sender fee) × rate - receiver fee

Expense formula:

    THB cost = (foreign expense + sender fee) × rate + receiver fee

THB requires no quote. Foreign currency requires an owned, matching, unexpired quote.
The result, settlement-day delay, and quote are returned. This function does not
write to the database.

### scenario_snapshot(owner, data)

Loads the requested current state version, copies its snapshot, and applies expense
overrides for a budget scenario. Only existing expenses may be overridden.
Foreign-currency overrides are converted and linked to mock quote evidence.

Returns the bound FinancialState, derived snapshot, and FX evidence.

### create_scenario(actor, data, obj=None)

Builds and saves one immutable essential, expected, or higher_cost scenario revision.
It calls scenario_snapshot and forecast, stores inputs and results, increments the
scenario-type revision, and records an audit event.

### create_loan(actor, data, obj=None)

Calls loan_schedule, saves the immutable simulation and its full result, and creates
an audit event. It does not create an application, approval, or balance change.

### create_source(actor, data, obj=None)

Creates a funding source with a stable economic_key to prevent duplicate real-world
funding identities. Supported types are family, scholarship, external_savings, and
loan.

Loan funding must reference an owned LoanSimulation and exactly match its currency
and net proceeds. Availability is an explicit estimate. An undisbursed loan must
remain estimated and cannot be marked as opening funds.

### evaluate_plan(owner, scenario, allocations)

Deterministically evaluates a combined funding plan.

It checks:

- Current state version and scenario freshness.
- Unique funding source allocation.
- Allocation greater than zero and within source capacity.
- Opening funds and already received funds are not counted again.
- Required FX quote, net receipt, and settlement date.
- Funding does not predate the opening snapshot.
- Loan repayment events are included across the full saved schedule.
- Uncertain sources remain explicit assumptions.

The result is feasible, feasible_under_assumptions, incomplete, or funding_gap.
The function returns a result without saving it.

### create_plan(actor, data, obj=None)

Loads the owned scenario, calls evaluate_plan, saves the immutable plan and result,
and records an audit event.

### compare_loans(actor, data, obj=None)

Loads two to ten owned simulations and returns their net proceeds, total repayment,
total cost, maximum installment, and affordability result. It reports whether the
loans share the same net-receipt basis. It deliberately does not select or rank a
loan for the student.

## Execution service functions

Location: finance/execution_services.py

### wallet(owner)

Returns the student's isolated DemoWallet or raises a validation error if it has not
been initialized.

### available(item)

Returns settled wallet balance minus amounts held by pending or unknown payments.
Draft, authorized, failed, cancelled, settled, and reconciled tasks do not create
holds.

### initialize(actor, data, obj=None)

Creates one demo wallet from the selected current financial-state opening balance and
as-of date. The opening snapshot becomes fixed for the demo.

### advance_clock(actor, data, obj=None)

Moves the demo date forward by at most 730 days. The date cannot move backward.

### B application and repayment services

Application functions now live in `backend/finance/lending_applications.py`:

- create_application: owned immutable B quote, one application, first due date in the future.
- application_action: versioned submit/cancel; submit automatically evaluates monthly affordability.
- application_decision: operator re-evaluation of UNDER_REVIEW, without an approval override.
- disburse: rechecks current affordability; records cash/account/ledger atomically or returns to review.

`backend/finance/lending_ledger.py` creates loan accounts and installments and repays the earliest due installment using the shared Django wallet. Repayments respect payment holds, update state and audit atomically, and close the account after the last installment. `backend/finance/c_adapter.py` exports authoritative records and creates C mock explanations from an owned scenario.

The former execution_services application/decision/disbursement_action implementation has been removed. See [the replacement API](guide.md) for payloads and states.

### create_beneficiary(actor, data, obj=None)

Creates an immutable mock beneficiary destination owned by the student.

### verify_beneficiary(actor, data, obj)

Controlled operator action that marks or revokes mock beneficiary verification.
Verification does not authorize a payment.

### check_plan(plan)

Recalculates the plan with current inputs. Execution requires a complete feasible
plan using confirmed funding and expenses. Stale state or expired FX quotes cause
validation failure.

### create_payment(actor, data, obj=None)

Creates a draft payment task from a confirmed expense.

It requires:

- A current feasible plan covering the expense date.
- A controlled verified beneficiary.
- The same beneficiary ID confirmed on the expense.
- A positive confirmed THB amount and due date.
- No existing active or completed payment for the same event.
- A demo date no later than the expense due date.

### authorize(actor, data, obj)

Student action that authorizes a draft payment for 60 to 3,600 seconds. It rechecks
the current state, plan, and beneficiary. Audit details bind the authorization to
state version, plan, beneficiary, amount, currency, mock fee, and expiry.

### cancel(actor, data, obj)

Cancels a draft or authorized payment and clears its authorization. Submitted tasks
must be resolved through the adapter outcome flow.

### submit(actor, data, obj)

Rechecks authorization expiry, current state, plan, beneficiary verification, demo
deadline, settled wallet funds, active holds, and minimum reserve. A valid task
becomes pending and reserves its amount through available-balance calculation.
No ledger debit occurs yet.

### payment_event(actor, data, obj)

Controlled operator callback for a pending or unknown task.

- unknown retains the hold.
- failed releases the hold by changing status.
- settled creates one negative ledger entry, debits the wallet, adds ledger sequence
  to the expense, appends a state version, and stores a simulated receipt.

Repeated settled callbacks return the same result and cannot duplicate the debit.

### reconcile(actor, data, obj)

Matches a settled receipt against the task's expense ID, amount, beneficiary, and
ledger debit. Only then does the payment become reconciled.

### receive_funding(actor, data, obj)

Controlled operator settlement for family, scholarship, or external-savings sources.
It verifies availability and FX settlement date, credits the wallet exactly once,
creates one positive ledger entry, appends a state version, marks the source
received, and records an audit event. Loans must use the application/disbursement
flow.

## Financial-state functions

### json_value(value)

Location: finance/services.py

Converts Decimal, date, UUID, and related validated Python values into JSON-safe
values without losing decimal string precision.

### save_state(owner, expected_version, snapshot)

Location: finance/services.py

Locks the user row, verifies optimistic expected_version, validates protected demo
fields, appends a new immutable FinancialState, and creates an audit event.

Once the demo wallet exists:

- opening balance, as-of date, and currency cannot be rewritten;
- submitted or executed expenses cannot be rewritten;
- ledger-generated loan/repayment/received events cannot be removed or forged;
- settled_sequence is controlled by the ledger.

### VersionConflict

Returns HTTP 409 when the caller supplies a stale state version.

## Generic API functions and classes

Location: finance/workflow_api.py

### CommandView.post(request, pk=None)

Provides common behavior for all workflow POST commands:

- Enforces authentication and optional operator role.
- Loads the target using student ownership rules.
- Locks the student's user row to serialize financial commands.
- Requires an Idempotency-Key header.
- Rejects reuse of a key with a different request body.
- Runs the serializer and business handler atomically.
- Saves and replays the exact response for safe retries.

### ReadView.get(request, pk=None)

Returns owner-scoped paginated lists or one owner-scoped detail record. Calendar
views return a scenario timeline. Wallet reads add available_balance after holds.

### ResourceView.get(request)

Connects resource collection GET behavior to ReadView while retaining CommandView
POST behavior.

### resource(...) and command(...)

Location: finance/workflow_urls.py

Factory functions used to register consistent REST resource and workflow-command
routes without duplicating view classes.

## Validation layer

StrictInputMixin rejects every unknown or read-only JSON field. MoneyField uses exact
non-negative values with two decimal places for the THB-oriented core API.

The serializers additionally validate:

- Supported currencies and JPY precision.
- Dates, horizon, list sizes, IDs, choices, and text lengths.
- Source and beneficiary ownership.
- Confirmed events requiring amount and date.
- Unique event IDs and events not preceding the opening snapshot.
- Explicit FX fees, settlement delay, and loan withheld fee.

Business validation stays in service functions so the same rule applies whether the
caller is the frontend, an extraction service, a script, or another API client.

## Database-enforced functions

Migration finance/migrations/0004_immutable_records.py installs
studyflow_reject_history_change(). PostgreSQL invokes it before UPDATE or DELETE on:

- finance_financialstate
- finance_auditevent
- finance_demoledgerentry

This provides database-level append-only protection in addition to API checks.

## Demo command

The seed_demo management command creates isolated fictional student/operator users,
a mock beneficiary, one financial state, the three budget scenarios, two loan
simulations, and private local credentials. It refuses to overwrite existing demo
users and performs no approval, disbursement, or payment.

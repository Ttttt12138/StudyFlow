STUDYFLOW - BACKEND FLOW DESIGN
Version: Proposed v2 design | October 4, 2026
Scope: Role B backend, with interfaces to A (frontend) and C (AI/data).
This is an implementation proposal, not a description of existing code.

1. SYSTEM OVERVIEW

A: Frontend
    |
    v
Backend API -> identity/access checks -> domain services -> database
                                         |
                     +-------------------+------------------+
                     |                   |                  |
                 C: extraction      calculation engine   sandbox adapters

External documents and model output are untrusted input data.
Only backend commands may mutate confirmed state or execution records.
Calculations use explicit inputs and exact monetary arithmetic.
All demo financial effects are labeled simulated.

2. NEW STUDENT FLOW

[Create student profile and planning horizon]
    -> [Upload document or submit official-source URL]
    -> [C extracts candidate fields with evidence]
    -> [Backend validates format, amount, currency, dates, duplicates]
    -> [A shows known / estimated / missing fields]
    -> [Student confirms or corrects]
    -> [Backend commits a new financial-state version]
    -> [Complete expense dates and funding assumptions]
    -> [Calculate three budget scenarios]
    -> [Show dated balances, calendar, and funding gaps]
    -> [Combine funding sources]
    -> [Validate plan]
         -> incomplete/late funding: show reasons and revise
         -> borrowing included: calculate loan simulation
         -> feasible under assumptions: save versioned plan
    -> [Optional simulated application]
    -> [Controlled simulated decision]
    -> [Schedule and settle simulated disbursement]
    -> [Record demo ledger credit exactly once]
    -> [Recalculate state and funding gaps]
    -> [Separate payment authorization and sandbox payment flow]

Application approval is not disbursement.
A scenario assumption is not money currently available.

3. EXISTING STUDENT FLOW

[Import account snapshot and transaction/invoice data]
    -> [Validate and deduplicate candidate events]
    -> [Confirm uncertain obligations or recurrence candidates]
    -> [Commit state version]
    -> [Forecast and detect risk]
    -> [Propose and validate funding strategies]
    -> [Receive and verify any simulated incoming funds]
    -> [Recalculate]
    -> [Authorize payment]
    -> [Execute, settle, reconcile, and audit]

Define the opening snapshot cutoff. Transactions already included in that
snapshot must not be applied again.

4. SOURCE INGESTION AND CONFIRMATION

A -> backend: upload file or submit URL.
Backend: store source metadata, content hash, retrieval time, and access owner.
C: produce candidate fields, source locations, and missing-field explanations.
Backend:
- Validate schema, currency, precision, dates, ownership, and duplicate identity.
- Preserve conflicts instead of choosing a value silently.
- Do not follow document instructions as tool commands.
- For URL retrieval, reject local/private-network destinations, validate redirects,
  and limit content size/type. Treat website content as evidence, not authority.
A: show evidence and allow corrections.
Student -> backend: confirm fields with expected state version.
Backend transaction:
- Check expected version and validation.
- Write immutable domain revisions and their evidence links.
- Append state version and audit event.
- Commit; trigger recalculation.

A stale expected version returns a conflict and requires refreshing the view.
User confirmation does not independently verify an external source.

5. BUDGET / FORECAST FLOW

Input:
- State version and account snapshot cutoffs.
- Scenario revision and planning horizon.
- Dated expense revisions and funding assumptions.
- Reserve rule.
- Explicit FX quote snapshots and fee/settlement assumptions.

Validation -> normalize supported currencies -> construct dated events
    -> order events -> calculate balances -> identify gaps
    -> persist immutable calculation inputs/results -> return UI result.

Balance(t) = opening available funds + included inflows through t
             - outflows through t.
Cash shortfall(t) = max(0, -Balance(t)).
Reserve gap(t) = max(0, required reserve(t) - Balance(t)).
Required top-up = maximum reserve gap over the horizon.

Return first gap date, minimum balance, maximum gap, event timeline,
calculation version, completeness, and assumptions.
The maximum gap is a top-up-at-or-before-needed-date measure. Arbitrary staged
funding must be evaluated through its actual dates, not just this total.
Missing fees are not zero. Missing FX prevents affected totals.
If same-day arrival ordering is unknown, use a documented conservative rule.
Estimated income is included only in explicitly identified scenario assumptions.

Three scenario names are a team decision. Suggested defaults:
essential, expected, higher-cost. Never invent source-backed fees to fill them.

6. COMBINED FUNDING FLOW

[Select funding sources and allocations]
    -> validate ownership and unique economic source identity
    -> check amount remaining after other active commitments
    -> convert using recorded rates and deduct fees
    -> determine availability/settlement dates
    -> run forecast with allocated net proceeds
    -> report feasible, incomplete, late, or insufficient with reasons.

Do not count the same account funds as both opening balance and new income.
Do not reserve capacity across mutually exclusive draft scenarios.
When a plan becomes an active commitment, enforce capacity atomically.
Scholarships and family promises retain certainty/evidence labels.
Installments revise obligation dates after confirmed approval; they are not income.

7. LOAN SIMULATION FLOW

[Select immutable mock loan-product terms]
    -> [Validate supported rate/fee/grace-period rules]
    -> [Calculate net disbursement]
    -> [Generate full repayment schedule]
    -> [Check funding timing]
    -> [Evaluate repayment cash flow if sufficient income/expense evidence]
    -> [Persist simulation and schedule]

Net proceeds = principal - fees withheld at disbursement.
Separately paid and financed fees require distinct accounting.
Return every repayment, total interest, fees, total repayment, and conventions.
Affordability: insufficient_information if necessary income/expense data is absent.
A successful scenario check is not a real lender decision.

8. SIMULATED APPLICATION AND DISBURSEMENT

Application:
DRAFT -> SUBMITTED -> UNDER_REVIEW -> APPROVED or REJECTED.
DRAFT or pre-decision states may transition to CANCELLED under explicit rules.
Decision commands require an authorized demo operator or controlled mock adapter.
An LLM cannot invoke decision or disbursement authority.

Disbursement:
SCHEDULED -> PROCESSING -> SETTLED or FAILED.
PROCESSING may become UNKNOWN after timeout.
UNKNOWN -> SETTLED or FAILED only after adapter status resolution.
Cancellation is permitted only before dispatch.
Settlement must not occur before the effective disbursement date on the demo clock.

On settlement, in one database transaction:
- Deduplicate adapter event and settlement reference.
- Lock/check disbursement state and application approval.
- Create one ledger transaction and its postings.
- Mark disbursement settled and link ledger transaction.
- Append state version and audit record.
- Commit; schedule forecast refresh.

UNIQUE(disbursement_id) on its ledger settlement link prevents duplicate credit.
Use the original stable operation ID for status queries and retries.
Approval alone writes no ledger posting.

9. PAYMENT FLOW

[Create payment task from current validated plan]
    -> [Policy checks]
    -> [Show exact authorization summary]
    -> [User authorizes amount, beneficiary, fees, expiry, versions]
    -> [Pre-execution recheck]
    -> [Reserve spend capacity and queue dispatch atomically]
    -> [Sandbox adapter using stable idempotency key]
    -> [Submitted / pending]
    -> [Settled + verified receipt]
    -> [Ledger debit exactly once]
    -> [Invoice matching]
    -> [Reconciled]

Check balance freshness, active holds, beneficiary revision, limits, quote expiry,
authorization revocation/expiry, current versions, and duplicate obligations.
A hold reduces spendable funds; settlement replaces/releases it atomically.
A timeout preserves the hold while the outcome is unknown.
Definitive pre-settlement failure/cancellation releases the hold.
Do not call a provider inside a long database transaction. Use an outbox job,
stable operation key, status lookup, and recovery worker.
A submitted request is not settlement; settlement is not invoice reconciliation.
Partial matches remain partially reconciled. Amount alone is insufficient evidence.

10. VERSION AND RECALCULATION FLOW

New confirmed inputs -> new immutable state version.
Correction -> new revision referencing prior revision; never erase old evidence.
Budget edit -> new scenario revision.
Funding edit -> new plan revision.
Calculation -> immutable run bound to versions, input snapshots, engine version.
Authorization -> bound to exact task/plan/beneficiary/quote/amount summary.
Changed material inputs -> invalidate stale execution readiness -> revalidate
and require new authorization where the authorized terms no longer match.

Read-time freshness checks prevent stale results being presented as current.
Background recalculation failure must not hide stale status.

11. MAIN FRONTEND API GROUPS (PROPOSED)

Sources and candidates: upload, inspect evidence, confirm/correct.
State: read snapshot, history, current version.
Budgets: scenario revisions, calculate, dated calendar, gap results.
Funding: sources, plan revisions, validation.
Loans: mock product snapshots, simulations, repayment schedules.
Applications: create, submit, inspect; privileged mock decisions.
Execution: authorize, revoke, inspect task/status/receipt.
Audit: scoped read-only history.
Demo: isolated seed/reset and fixed-clock control, unavailable in production.

All reads/writes are student-scoped. Financial write endpoints use idempotency.
Validation returns structured field errors; version conflicts return explicit conflict.
No client-provided calculated total is trusted without backend recomputation.

12. ACCEPTANCE WALKTHROUGH

Fixture A: 80,000 THB - 9,000 rent - 65,000 tuition = 6,000;
15,000 reserve gives a 9,000 gap.
Fixture B adds 9,400 living expenses: -3,400 balance and 18,400 reserve gap.
Funding after tuition leaves the earlier gap.
Application approval leaves balances unchanged.
Repeated settlement produces one ledger transaction.
Missing income returns insufficient_information.
Changed authorization inputs prevent stale execution.
Timeout recovery never creates a duplicate payment.
